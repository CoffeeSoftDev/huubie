Detalle

El punto 35 pide usuario, fecha y hora de seis acciones. Cada acción escribe un renglón en el momento en que pasa, desde el controlador que la ejecuta. La bitácora solo crece: nadie la edita ni la borra.

AcciónCuándo se escribeDónde en el códigoQué guarda

ConfirmaciónAl confirmar el reparto de un día, de un mes o de un folio; también al rehacer un día («Sí, rehacer»)ctrl-facture2-tickets.php · abrirCorrida()Folio GEN, día, meta, total, 16%, 0% y tickets; al rehacer, la corrida que reemplaza

Por decidir

PreguntaPropuesta
El documento separa «Generación» de «Confirmación». ¿Se registra también cada vista previa?No: la vista previa no escribe nada y se pide muchas veces. Solo la confirmación deja renglón.
«Eliminación» no está en el punto 35Agregarla: eliminar un día borra tickets ya entregados, y es la acción que más preguntas va a generar.
¿Cuánto tiempo se guarda?Siempre. Son pocos renglones al día (decenas, no miles).
¿Quién ve la bitácora?Solo el administrador, en Configuración, con el permiso catalogos que ya existe.

Una sola tabla para las seis acciones. El nombre del usuario se guarda como copia, igual que en import_batch y generation_run: la bitácora se tiene que poder leer aunque el usuario se borre. 

CREATE TABLE audit_log (
    id          INT(11)      NOT NULL AUTO_INCREMENT,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    action      VARCHAR(30)  NOT NULL COMMENT 'importacion · confirmacion · reasignacion · catalogo · reimpresion · eliminacion',
    entity      VARCHAR(40)  NOT NULL COMMENT 'tabla afectada: import_batch, generation_run, product, branch, virtual_ticket…',
    entity_id   INT(11)      NULL     COMMENT 'id de la fila afectada',
    label       VARCHAR(120) NOT NULL COMMENT 'lo que se lee en la lista: archivo, GEN-000001, PTE010, 4510…',
    detail      JSON         NULL     COMMENT 'antes y despues, o el resumen de la accion',
    user_id     INT(11)      NULL     COMMENT 'quien tecleo su PIN (tabla user)',
    user_name   VARCHAR(100) NULL     COMMENT 'copia del nombre',
    branch_id   INT(11)      NULL,
    PRIMARY KEY (id),
    KEY idx_audit_branch_fecha (branch_id, created_at),
    KEY idx_audit_accion       (action),
    KEY idx_audit_entidad      (entity, entity_id)
);

Reglas

  • Solo INSERT. Ningún controlador hace UPDATE ni DELETE sobre audit_log.
  • El renglón se escribe después de que la acción salió bien: una carga que falla no deja una importación en la bitácora.
  • Un solo método en el modelo, createAuditLog(), y un ayudante en cada controlador que le pone usuario, sucursal y fecha.
  • «Tickets reimpresos» de Reportes (punto 28) sale de contar las reimpresiones de esta tabla.
