Vista de documento para el ERS

El ERS no es una respuesta de chat: es el documento con el que arranca un proyecto y que se revisa con el cliente. Hoy sale como markdown suelto —y en avatars, dentro de un bloque de código en monoespaciada—. La propuesta es que se vea como lo que es: una hoja de documento, con portada, índice y secciones, reusando el papel que el visor ya usa para los .md.

01 Descripción breve del proyecto

Es un sistema que se encarga del control de tickets y sus diferentes medios de pago asociados a cada transacción. Su objetivo principal es generar un concentrado ordenado de tickets, diferenciando claramente entre tickets facturados y no facturados.

El sistema deberá permitir la selección de una fecha para consultar los tickets emitidos: los que se facturaron y los de tarjeta de crédito.

02 Objetivo del proyecto

Permitir controlar mediante un sistema un monto correcto de venta aplicando técnicas de cálculo de porcentaje, donde el 70% es la meta de venta facturada y el 30% restante no lo es.

05 ¿El éxito del proyecto se da cuándo?
Consultar tickets por fecha. Selecciona un día y ve todos los tickets ordenados cronológicamente, identificando los bloqueados (facturados) y los pendientes.
Calcular el porcentaje de venta al 16%. Ejemplo: de $31,843.90 del día 10, el monto a facturar es $19,312.43 y lo ya facturado, $2,978.30.
Alcanzar la meta de facturación. Al menos el 70% de ventas facturadas al 16%; si no se llega, el sistema muestra la cifra alcanzada.
Imprimir tickets virtuales. El sistema genera y muestra un ticket listo para impresión.
06 Acciones a realizar

Fase 1 · Análisis

  • Crear la base de datos con los campos requeridos y su diagrama ER.
  • Definir las tablas principales que no se modificarán.
  • Desarrollar templates para entender el funcionamiento.

Fase 2 · Administrador

  • Módulo para subir el archivo de ventas diarias por mes.
  • Módulo para subir la lista de facturas por mes y año.
  • Módulo de administración de métodos de pago.

Fase 3 · Resumen de ventas

  • Apartado de consulta del acumulado total real.
  • Apartado de no facturado (solo formas de pago bancarias).
  • Apartado de orden facturado por rango de fechas.

Por qué así

  • Es el papel que el visor ya usa

    Mismo fondo #FAF7F2, misma serif Lora y la franja terracota de .md-rendered. No es un estilo nuevo: es el documento de siempre.

  • Portada e índice

    El cliente ve de qué va y cuánto hay antes de leer. El índice ancla a cada sección.

  • Los módulos son fichas, no párrafos

    Nombre, pestaña y campos en columnas: es la parte que después se vuelve criterios de aceptación.

  • Las fases se leen como plan

    Timeline vertical en vez de tres listas sueltas.

  • Trazabilidad al pie

    Qué archivos se leyeron para levantarlo: es lo que separa un ERS real de uno inventado.

El botón que cierra el flujo: "Generar historias" manda al chat "deriva las historias de este ERS" con el documento como contexto. Carpeta → ERS → historias sin copiar y pegar nada.
Imprimir sale gratis: al ser una hoja de verdad, window.print() con un @media print corto da el PDF que se manda al cliente.

Para el ancho del chat: cabecera con los números del proyecto y las ocho secciones plegadas. Se abre la que interesa y, para leerlo completo, el botón Documento lleva a la hoja.

Qué habría que tocar

  1. La regla del agente

    Una sección en ers.md con el bloque ```ers: las mismas ocho secciones que ya escribe, pero como datos. El campo archivos formaliza la trazabilidad que hoy pone a mano.

  2. El renderer

    renderErs() en ia-render.js, junto a renderStories(). Reusa su parser YAML: no hay motor nuevo.

  3. El CSS

    Clases .ia-ers-* heredando de .md-rendered (papel, serif, franja). Se agrega el @media print para el PDF.

  4. Las salidas

    Copiar markdown, descargar .md, guardar en los documentos del proyecto e imprimir. Y el botón Generar historias, que encadena con el paso siguiente.

  5. Las tres superficies

    Visor, avatars-sandbox y avatars-playground comparten ia-render.js: se implementa una vez.

Degradación: si el modelo entrega el ERS en markdown plano (sin el bloque), se sigue viendo como hoy. El render nunca rompe el mensaje: si el bloque no cumple el esquema, queda como código.
Recomendación: implementar A + B como una sola tarjeta con el botón para alternar —ficha por defecto en el chat, hoja al expandir—, y dejar el Generar historias del pie: es lo que convierte carpeta → ERS → historias en un flujo continuo en vez de tres pasos sueltos.
